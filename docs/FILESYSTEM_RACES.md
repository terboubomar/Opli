# Filesystem race audit — Milestone 0

The copy-only executor in `src-tauri/src/recipe.rs` rejects a changed source digest, an occupied destination, and a symlink in an existing output parent. A Windows regression test also confirms rejection of an existing output junction. It uses `create_new` for a temporary file and a hard link to publish completed bytes without replacing an existing filename. The Windows unit tests and desktop smoke test confirm those ordinary cases. They do **not** prove safety against another process changing path components concurrently.

## Remaining race

`check_parents` and `ensure_parents` inspect pathnames, then `OpenOptions::open`, `File::open`, `fs::hard_link`, and `fs::remove_file` resolve pathnames again. A concurrent process with write access to an output ancestor can replace a directory or reparse point between these calls. The temporary write, final link, or cleanup could then refer to a different directory from the one shown in preview. The source is likewise reopened by pathname after its digest check; content hashing catches changed bytes but does not pin file identity across all opens. The in-process `PlanStore` mutex only makes a token single-use; it cannot stop another process from changing the filesystem.

## Platform protection to implement before claiming adversarial path safety

- **Windows:** open and retain handles for the output root and each traversed directory, using directory-open semantics and no `FILE_SHARE_DELETE`; reject reparse points, including junctions and mount points, using handle attributes and compare file IDs before publication. Pin the source through a handle and hash/copy that same object. Rework final publication so all path resolution is tied to those pinned directories, or fail closed when the platform cannot provide that guarantee. Test directory replacement and junction swaps from a second process. Microsoft documents directory handles, `FILE_FLAG_OPEN_REPARSE_POINT`, and the fact that omitting `FILE_SHARE_DELETE` blocks later delete/rename opens in [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew); it documents the reparse attribute in [Reparse Point Operations](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-operations).
- **macOS:** traverse from an opened directory descriptor using `openat` with no-follow checks, create the private temporary file relative to the retained destination directory descriptor, and publish with an exclusive, descriptor-relative operation such as `renameatx_np` with `RENAME_EXCL` where the volume supports it. Keep the source descriptor open for hashing and copying. Verify APFS and non-APFS/network behavior on a real Mac; fail closed if the required exclusive operation is unavailable. Apple documents [`O_NOFOLLOW`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/open.2.html) and [descriptor-relative exclusive rename APIs](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/ToolsandAPIs/ToolsandAPIs.html).

`CreateHardLinkW` is documented as NTFS-specific, with some SMB support and no ReFS support, so hard-link publication must be tested per destination filesystem or replaced by another exclusive publication method; a failed hard link currently becomes a per-file failure and leaves the source intact. See [Microsoft CreateHardLinkW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw). Do not substitute a normal overwrite-capable rename or copy directly to the visible destination.

**Status:** identified and documented; platform-specific hardening and adversarial swap tests remain open. The M0 gate is open.
